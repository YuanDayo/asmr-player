## 问题一：新安装后不弹「首次启动介绍 / 使用须知 / 免责宣言」

### 1.1 现象
全新安装（DataStore 为空）首次进入，没有弹出 5 页功能引导，也没有出现使用须知与免责声明。

### 1.2 定位到的可能原因（按概率排序）

**根因 A（高）：`onboardingSeen` 的 `null`/`false` 语义被读盘兜底破坏。**

- `data/SettingsStore.kt:114` 定义 `val onboardingSeen: Boolean? = null`，注释明确：
  `null` = 「盘还没读到」，`false` = 「读到了、确实没看过」。
- 但 `SettingsStore.kt:235` 读盘时写成：
  ```kotlin
  onboardingSeen = p[Keys.ONBOARDING_SEEN] ?: false
  ```
  这把「从未写过该 key 的新安装」直接兜底成了 `false`，而不是保持 `null`。
- 触发判断在 `ui/AppRoot.kt:424-426`：
  ```kotlin
  LaunchedEffect(settings.onboardingSeen) {
      if (settings.onboardingSeen == false) onboardingOpen = true
  }
  ```
  由于读盘永远给 `false`（不是 `null`），此判断对新安装**理论上仍会弹**，但存在两个隐蔽断点：
  - `MainViewModel.kt:1791` 用 `_settings.value == AppSettings()` 判断「首帧」，而 `AppSettings()` 默认 `onboardingSeen = null`，一旦有别的逻辑在首帧前后写入了别的 key，`onboardingSeen` 的 `null→false` 时序错位，`LaunchedEffect` 只在 `null→false` 变化时触发一次，可能漏触发。
  - `AppRoot.kt:427-441` 的「版本日志」效应与「首启引导」效应**共享 `settings.seenVersion` / `settings.onboardingSeen` 两个 key**，`onboardingSeen == false` 分支会 `return`（第 432 行 `Unit`），若顺序/时序错位，引导会被版本日志逻辑抢先置位，导致引导永远不再弹。

**根因 B（中）：免责/须知根本没进首启流程。**

- `ui/LegalPage.kt` 的 `LegalTextPage` 目前只挂在设置页二级页：
  `ui/SettingsScreen.kt:585-586`（`SettingsPage.TERMS` / `SettingsPage.DISCLAIMER`）。
- 需求要求「新安装后弹出使用须知与免责宣言」，但 `ui/OnboardingScreen.kt` 的 `Pages` 只有 5 页功能说明，**没有法律条款页**，首启流程里也从未调用 `LegalTextPage`。
- 结论：即便引导弹出，用户也看不到「使用须知 / 免责声明」，需要在首启引导里补上（或作为引导的最后一步 / 独立确认页）。

### 1.3 需检查的配置 / 状态 / 模块
| 模块 | 文件 | 关注点 |
|---|---|---|
| 状态定义 | `data/SettingsStore.kt` | `onboardingSeen` 默认值与读盘兜底（第 114、235 行） |
| 触发逻辑 | `ui/AppRoot.kt` | 第 424-441 行两个 `LaunchedEffect` 的时序与互斥 |
| 状态初始化 | `ui/MainViewModel.kt` | 第 61-62、1786-1810 行的 `_settings` 首帧与 collect |
| 引导 UI | `ui/OnboardingScreen.kt` | `Pages` 列表，缺法律页 |
| 法律文案 | `ui/LegalPage.kt`、`res/values/strings.xml` | `terms_of_use` / `disclaimer` 已存在，可复用 |
| 备份恢复 | `SettingsStore.kt:408` | `overwriteAll` 里 `onboardingSeen ?: true` 的语义需保持一致 |

### 1.4 修复策略（最小改动，二选一，优先 A）

**策略 A（推荐，最贴合现有注释语义）：恢复 `null` 语义。**

1. `SettingsStore.kt:235` 改回「保留 null」：
   ```kotlin
   onboardingSeen = p[Keys.ONBOARDING_SEEN],
   ```
   （去掉 `?: false`，让「从未写盘 = null = 还没读」与「写过 false = 确实没看」区分开。）
2. 核对 `AppRoot.kt:424-441` 两段效应的触发顺序：确保首启引导的 `LaunchedEffect` 在 `null→false` 时可靠触发，且不被「版本日志」效应抢先 return。
3. 在 `OnboardingScreen` 的最后一步（或作为第 6 页）加入「使用须知 + 免责声明」的展示与「我已阅读并同意」确认；复用 `LegalTextPage(R.string.terms_of_use)` 与 `LegalTextPage(R.string.disclaimer)`。首启关闭（跳过/完成）时才写 `markOnboardingSeen()`（`MainViewModel.kt:1726` 已存在）。

**策略 B（替代）：引入独立「首启未完成」标记。**

若担心改动 `null` 语义影响老用户（升级场景），可新增一个 `onboardingDone: Boolean`（默认 `false`，新安装才为 false，老安装迁移时置 true），引导依据它而不是 `onboardingSeen`。此方案改动面更大，仅在策略 A 验证不通过时采用。

### 1.5 实施步骤
1. 改 `SettingsStore.kt:235` 读盘兜底（策略 A）。
2. 在 `OnboardingScreen.kt` 增加法律条款页（复用 `LegalTextPage`），并在完成回调里保留 `markOnboardingSeen()`。
3. 复核 `AppRoot.kt` 触发逻辑，消除与「版本日志」效应的时序竞态。
4. 编译 + 单测（`testDebugUnitTest` 已有 `VersionConsistencyTest`，检查是否覆盖 `onboardingSeen`）。

### 1.6 验证方法与验收标准
- **验证**：清数据重装（或 `adb shell pm clear <pkg>`）后冷启动，观察是否弹出引导；完成后杀进程重启，确认不再弹。
- **验收标准**：
  - 全新安装必弹引导，且引导内含「使用须知」与「免责声明」，需用户确认。
  - 完成/跳过后写盘一次，之后冷启动不再弹。
  - 老用户（已有 `seenVersion`）升级后**不**被强制重看引导。
  - 「设置 → 关于 → 功能介绍」仍可手动重看（`replayOnboarding`，`AppRoot.kt:417-423`）。

## 问题二：缓存增长过快、体积容易过大

### 2.1 现象
应用缓存目录持续膨胀，长时间使用后体积过大，无回收/上限，也无清理入口。

### 2.2 定位到的可能原因

**根因 A（高）：Coil 磁盘缓存写死 256MB，无增长上限与清理策略。**
- `AsmrApplication.kt:28-33`：
  ```kotlin
  .diskCache {
      DiskCache.Builder()
          .directory(cacheDir.resolve("coil"))
          .maxSizeBytes(256L * 1024 * 1024)
          .build()
  }
  ```
  256MB 上限偏大；且 Coil 磁盘缓存的 LRU 只在「命中/写入时」触发淘汰，长期不清会顶满。

**根因 B（中）：内存缓存 25% 堆，设备内存小则占比过高。**
- `AsmrApplication.kt:27`：`maxSizePercent(0.25)`，低端机 25% 堆可能引发 GC 压力；虽不直接占磁盘，但配合磁盘缓存放大整体占用。

**根因 C（中）：存在第二层封面文件缓存，无统一上限。**
- `LibraryRepository.artworkFile`（见 `AsmrApplication.kt:22` 注释）按 `path+size+mtime` 键控的文件缓存，与 Coil 磁盘缓存**两层并存**，各管各的，缺少总配额与清理入口。

**根因 D（低）：无用户可见的缓存管理/清理入口。**
- 设置页未提供「清理缓存 / 查看缓存大小」入口，用户只能去系统设置清。

### 2.3 需检查的配置 / 状态 / 模块
| 模块 | 文件 | 关注点 |
|---|---|---|
| 图片缓存 | `AsmrApplication.kt` | `memoryCache` / `diskCache` 的 maxSize |
| 封面文件缓存 | `data/LibraryRepository.kt` | `artworkFile` 的落盘路径与键控、是否有清理 |
| 清理入口 | `ui/SettingsScreen.kt` | 是否已有「缓存」相关分组/条目 |
| 下载临时文件 | `download/DownloadService.kt`、`domain/AsmrOneDownloads.kt` | 解压临时目录、失败残留是否清理 |
| 应用日志 | `data/AppLog.kt` | 日志文件是否设上限/滚动 |

### 2.4 修复策略（最小改动）

1. **收紧 Coil 磁盘缓存上限**：`256MB → 128MB`（或更小，按封面实际占用评估），保持 `maxSizeBytes` 明确值。
2. **给 `artworkFile` 文件缓存加容量上限与 LRU 清理**（或在写前检查总大小，超过阈值删最旧条目）。
3. **（可选，低优先级）** 内存缓存 `0.25 → 0.15` 或按设备内存分档。
4. **新增「清理缓存」入口**（设置页），点击后清空 Coil 磁盘缓存（`context.cacheDir` 下的 `coil` 目录）与 `artworkFile` 缓存，并提示已释放的空间大小。若改动面受限，至少提供「查看缓存大小」。

> 说明：清理必须是「删缓存、不删用户数据」。曲库索引、播放历史、书签、分级、标签、下载的音频文件**一律不能碰**。只清 `cacheDir` 与封面临时缓存。

### 2.5 实施步骤
1. 调整 `AsmrApplication.kt` 缓存上限。
2. 排查 `LibraryRepository.artworkFile` 的清理逻辑，补上限。
3. 在设置页加「清理缓存」入口，调 `MainViewModel` 新增的清理方法。
4. 编译 + 单测；确认清理不影响「本机有没有」台账（`DownloadedLedger`）。

### 2.6 验证方法与验收标准
- **验证**：灌入大量封面后查看 `cacheDir/coil` 大小；触发清理后确认体积下降、列表封面仍正常加载（二次进入不重解码或可接受）。
- **验收标准**：
  - 磁盘缓存有明确上限，不再无限增长。
  - 提供清理入口，清理后不影响曲库/历史/书签/已购台账。
  - 清理是可重复、幂等的，不会误删用户文件。

## 问题三：皮肤为「经典」时底部播放栏显示异常

### 3.1 现象
切换到「经典（旧版）」皮肤（`SkinStyle.CLASSIC`，id `"classic"`）后，底部播放栏（悬浮导航胶囊 + 迷你播放条）显示异常（可能表现为：缺少玻璃高光/描边、纯色底与内容对比不足、栏体过透或过实、与其它皮肤观感不一致）。

### 3.2 定位到的可能原因

**根因 A（高）：经典皮肤下 `asmrFrost()` / `glassEdge()` / `asmrBorder()` 全部 no-op，栏失去层次。**

- `ui/AsmrCard.kt` 中三个关键样式函数都以 `if (!LocalEditorial.current) return this` 开头：
  - `asmrFrost()`（第 179-181 行）：非 iOS 玻璃皮肤直接返回原 Modifier，**不糊、不叠色**。
  - `glassEdge()`（第 126-127 行）：非 editorial 直接返回，**不画顶部高光**。
  - `asmrBorder()`（第 110-111 行）：非 editorial 返回空 Modifier。
- 底部播放栏（`AppRoot.kt` 的 `FloatingNavBar` 第 1227-1308 行、`MiniPlayer` 第 1347 行）都调用 `.asmrFrost().glassEdge(shape)` 与 `.background(asmrBarColor())`。
- 经典皮肤下：磨砂和高光都没了，只剩 `asmrBarColor()`（第 292-303 行）返回的 `scheme.surface.copy(alpha = LocalBarAlpha.current)`。栏体变成一块**半透明纯色**，压在滚动内容上时缺边界，文字与内容对比不足 → 显示「异常」。

**根因 B（中）：`LocalBarAlpha` 取值使经典皮肤栏过透。**
- `Theme.kt:417`：`LocalBarAlpha provides maxOf(0.78f, cardAlpha).coerceAtMost(1f)`。
- 用户截图里 `cardAlpha = 1.0`（UI 卡不透明度拉满），此时 `LocalBarAlpha = 1.0`，`asmrBarColor()` 对 classic（非 bright、非 editorial）走 `scheme.surface.copy(alpha = LocalBarAlpha.current)`，应仍是不透明 surface —— 需结合经典配色的 `surface` 亮度确认对比度。

**根因 C（中）：经典皮肤的 `surface` / `onSurface` 配色本身与「半透明栏」假设冲突。**
- `Theme.kt:200-209`（`lightScheme` 的 `SkinStyle.CLASSIC`）与 `251-259`（`darkScheme`）定义了经典配色，若其 `surface` 是近乎纯白/纯黑且栏叠加在内容上，缺失描边/高光后边界会糊。

**根因 D（低）：`bright` 判定把 classic 也归入「明快」分支，但栏样式没对应。**
- `Theme.kt:365`：`val bright = style == SkinStyle.BRIGHT || style == SkinStyle.CLASSIC`，`LocalIsBright` 被置 true。
- 但 `asmrBarColor()` 里 `LocalIsBright` 分支返回 `scheme.surface`（第 298-299 行），与「明快」的 2px 墨描边/硬投影视觉语言不完全一致，可能是「异常」观感的来源之一。

### 3.3 需检查的配置 / 状态 / 样式模块
| 模块 | 文件 | 关注点 |
|---|---|---|
| 栏样式函数 | `ui/AsmrCard.kt` | `asmrFrost`/`glassEdge`/`asmrBorder`/`asmrBarColor` 对非 editorial 的 no-op |
| 底栏渲染 | `ui/AppRoot.kt` | `FloatingNavBar`(1227)、`MiniPlayer`(1347) 的 modifier 链 |
| 皮肤配色 | `ui/theme/Theme.kt` | `lightScheme`/`darkScheme` 的 `CLASSIC` 分支；`LocalBarAlpha`(417) |
| 皮肤判定 | `ui/theme/Theme.kt` | `LocalClassicSkin`(118)、`LocalIsBright`(365)、`LocalEditorial`(363) |
| 明快装饰 | `ui/AsmrCard.kt` | `ClassicTicks`(326)、`asmrMenuBorder`(156) |

### 3.4 修复策略（最小改动）

1. **为经典皮肤补一条「栏的降级样式」**：在 `asmrBarColor()` / `glassEdge()` / `asmrFrost()` 的 `LocalClassicSkin` 分支，给出经典皮肤专属的底色/描边（例如经典皮肤下 `glassEdge` 画一条 `outlineVariant` 细描边或 `LocalIsBright` 的 2px 墨边，`asmrBarColor` 用更实的 surface）。**只新增 `LocalClassicSkin` 分支，不改 editorial 分支**，避免影响 iOS 玻璃皮肤。
2. 核对 `LocalBarAlpha` 对 classic 的取值，确保底栏不透明或半透明程度合理（有边界、文字可读）。
3. 若根因 D 成立，统一 `bright`/`classic` 的栏视觉语言（墨描边或降级实底），使底栏与「明快/经典」的硬描边风格一致。

### 3.5 实施步骤
1. 在 `AsmrCard.kt` 为 `LocalClassicSkin` 补降级样式（只动 classic 分支）。
2. 复核 `AppRoot.kt` 底栏 modifier 链，确保经典皮肤下有明确边界。
3. 编译 + 截图对比（经典 vs iOS 玻璃 vs 明快，浅/深色，宽/窄屏）。

### 3.6 验证方法与验收标准
- **验证**：`scripts/ui_verify.sh` 截图，切「经典」皮肤，观察底栏导航胶囊与迷你条在浅色/深色、有无正在播放曲目下的显示。
- **验收标准**：
  - 经典皮肤下底栏有清晰边界与可读文字，无「半透明纯色压内容糊成一团」。
  - iOS 玻璃、明快、深海等其它皮肤不受本次改动影响（回归截图无回归）。
  - 导航胶囊选中态、迷你条进度线、播放/暂停键均正常。

## 执行结果（2026-11-22，2.6.0-beta15）

三件事都已落库并通过模拟器验证。与计划书的偏差记在这里，避免下一轮又按旧结论改回去。

### 问题一：根因 A 不成立，改法不同

- `SettingsStore.settings` 里 `onboardingSeen = p[KEY] ?: false` 是**对的**，不能改回 `p[KEY]`：
  能走到 `?:` 那行说明 DataStore 已经吐过一次（盘读完了），`null` 只该留给 `_settings` 的初值。
  保留 `null` 会让 `AppRoot` 的 `== false` 永不成立 —— 新安装一辈子不弹。
  实测（模拟器 `pm clear` 后冷启动）beta14 上 5 页引导**是弹的**，缺的只有条款页（即根因 B）。
- 采用**版本化**（计划书策略 B 的轻量版）：`AppSettings.onboardingVersion: Int = 0` +
  `ONBOARDING_GUIDE_VERSION = 1`。触发分两档：`!seen` → 功能页 + 条款页；`seen && version < CUR`
  → **只补条款页**（老用户不被按回第 1 页，也不违反「升级不强制重看」）。
- `OnboardingScreen` 拆成「功能页」+「条款页」两段：条款正文复用 `LegalTextPage`，
  底部按钮在勾选前禁用；「跳过」只跳过功能页，条款仍要读要勾。

### 问题二：按策略做，另加封面临时缓存上限

- Coil 磁盘 256MB → 128MB；`artworkFile` 加 64MB 上限 / 48MB 目标，每 32 次写入 prune 一次。
- 新增 `data/CacheManager`（只清 `cacheDir`）+ 设置页「其他 → 清理缓存」（显示占用、确认框）。
  注意 Coil 的 `coil` 目录必须走 `diskCache.clear()`，直接删目录会让 journal 悬空。

### 问题三：根因 A 补一条更硬的

  改成非 editorial 一律 `return this.background(asmrBarColor())`。
